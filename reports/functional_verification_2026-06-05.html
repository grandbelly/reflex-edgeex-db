코드 (콜체인 확정)

edgeex_app/db.py
 34  _GLOBAL_POOL: asyncpg.Pool | None = None      # 모듈 전역 싱글톤
 39  async def get_pool():                          # 최초 1회 생성 후 캐시
 50      _GLOBAL_POOL = await asyncpg.create_pool(...)   # ← 생성 시점의 이벤트루프에 바인딩
 67  async def q(sql, ...):
 81      async with pool.acquire() as conn:         # ← 다른/닫힌 루프에서 호출 → "Event loop is closed"
 97      except asyncio.TimeoutError:               # ← RuntimeError를 못 잡음 (폴백 무력)
117      except Exception: ... raise                # → 페이지가 "Connection Error:" 토스트 + 0데이터

asyncpg 풀/커넥션은 생성된 이벤트루프에 종속합니다. 전역 캐시된 풀을 다른 루프(백그라운드 태스크 / 런타임 경과 후 새 루프)에서 acquire()하면 닫힌 루프로 새 커넥션을 시도 → loop.getaddrinfo → _check_closed() → RuntimeError: Event loop is closed. line 97 폴백은 TimeoutError만 잡아 이 RuntimeError를 못 살림.

2가지 고장 모드

모드대상증상
A. 백그라운드/실시간 refresh실시간 알람 페이지 + 전역 5초 폴러풀 생성 루프 ≠ 실행 루프 → 항상 "Event loop is closed" (재시작 직후에도). 5초 폴러가 전 화면에 "Connection Error" 토스트 살포
B. on_load 요청 핸들러대시보드·알람·예측·통신·태그뷰신선 시작 땐 요청 루프에 풀이 유효 → 정상. 그러나 런타임 경과로 그 루프가 죽으면 전멸 (대시보드 100→0)
권장 수정 (코드, db.py 한 파일 — 최적화보다 최우선):
  1. 전역 단일 풀 폐기 → 루프별 풀 캐시({id(loop): pool}) 또는 get_pool()에서 현재 루프 ≠ 풀 루프 / 풀 closed 감지 시 재생성
  2. 최소 핫픽스: q()에서 RuntimeError("Event loop is closed")도 잡아 풀 재생성 후 1회 재시도 (기존 direct-connect 폴백 확장)
  3. 백그라운드 refresh 태스크는 자신의 실행 루프에서 커넥션 획득하도록 보장
이건 인프라 튜닝이 아니라 정합성/안정성 코드 버그입니다. "기능검증 먼저 → 코드최적화" 원칙의 정확한 산출물 — 최적화 이전에 이게 먼저.
