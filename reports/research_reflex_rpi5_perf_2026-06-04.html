① 요약 (Executive Summary)

RPI5(ARM64) Docker 위 실시간 IoT 대시보드의 2025-2026 최고 레버리지 4가지:
  1. 프론트엔드는 Reflex 0.8의 Vite + Rolldown 파이프라인으로 빌드 — 구 Next.js 대비 벤더 주장 2-3배 빠르고 빌드 메모리 훨씬 적음(중립 벤치 ~3배, 피크 메모리 ~75%↓). 4-8GB Pi에서 결정적.
  2. ARM64 이미지를 QEMU 에뮬레이션으로 빌드하지 말 것 — cross-compile로. 에뮬은 모든 명령을 런타임 변환해 ~7배 느림. "여러 RPI에 복제 배포" 목표에 직결.
  3. asyncpg/SQLAlchemy 풀은 작게(엔진당 기본 pool_size=5 + max_overflow=10 = 15, 지연 생성이라 유휴 낭비 0) + timescaledb-tune으로 PostgreSQL 메모리/병렬/WAL을 Pi의 RAM·코어에 자동 맞춤.
  4. Reflex 내장 delta 프로토콜(변경된 dirty var만 WS 전송)에 기대고, 고빈도 이벤트엔 .throttle()로 페이로드 트래픽 절감.

② ✅ 검증 통과 권고 5건 (confirmed)

1. Reflex 0.8 Vite+Rolldown 빌드로 전환 high · merged 3-0 / 2-1

0.8이 Next.js 빌드를 Vite+Rolldown으로 교체 — 벤더 "2-3배 빠르고 메모리 훨씬 적음". 중립 벤치 corroborate: rolldown-vite 4.16s vs Next+Turbopack 12.88s(~3.1배), Rolldown 피크 메모리 ~1.2GB vs Rollup ~4.8GB(~75%↓). 4GB Pi에서 빌드 메모리를 봉투 안에 가두는 가장 큰 레버.

출처(primary): https://reflex.dev/blog/reflex-080/ · 주의: 2-3배는 벤더 릴리스 수치(Rolldown beta), 단 magnitude는 중립 소스가 재현.

2. ARM64 이미지는 cross-compile, QEMU 금지 high · 3-0

Docker 공식 엔지니어링 블로그(재현 벤치): 2번째 아키텍처를 cross-compile하면 빌드시간 +70%지만, QEMU 에뮬이면 "거의 7배". 학술 QEMU TCG 측정 2.5-21배(geomean ~7.7배). 실사례: ARM64 빌드 15분→2분(QEMU 탈출). 여러 RPI 복제 배포 → BuildKit cross-compile 또는 ARM 러너/Pi 네이티브 빌드.

출처(primary): https://www.docker.com/blog/faster-multi-platform-builds-dockerfile-cross-compilation-guide/ · 주의: 7x/70% 수치는 단일 Go 워크로드 — 언어/빌드별 배수 변동, 방향은 robust.

3. DB 풀은 보수적으로 (엔진당 5+10=15, 지연 생성) high · 3-0

SQLAlchemy 2.0 공식: pool_size 기본 5, max_overflow 기본 10, 동시 최대 = 15/엔진. "어떤 구현도 사전 생성 안 함 — 첫 사용까지 대기". async 엔진은 AsyncAdaptedQueuePool이지만 5+10 동일. 엔진당 풀 작게 유지 + 총 잠재 연결(= 워커수 × 풀)을 Pi의 PostgreSQL max_connections 한참 아래로.

출처(primary): https://docs.sqlalchemy.org/en/20/core/pooling.html · /engines.html

4. timescaledb-tune로 PostgreSQL 자동 right-size high · 3-0

감지된 CPU/RAM 기준으로 shared_buffers, effective_cache_size, maintenance_work_mem, work_mem, timescaledb.max_background_workers, WAL 조정. 아키텍처 무관 Go 바이너리 → ARM64 적용. Pi에서 timescaledb-tune 실행(또는 컨테이너 한도에 맞춰 --memory/--cpus 명시) 후 쿼리 벤치마크.

출처(primary): https://github.com/timescale/timescaledb-tune · 주의: --memory/--cpus 오버라이드 경로는 약한 지지(1-0) — 플래그는 존재하나 본 검증선 미확정.

5. delta 프로토콜 활용 + .throttle() high · merged 3-0 / 2-0

primary 문서 + 이 repo의 .venv 설치 소스로 확인: Reflex가 핸들러 중 dirty_vars 추적 → get_delta()가 변경 var만으로 WS 페이로드 구성 → _clean() 리셋. docstring "state가 커져도 성능 유지". .throttle(ms)은 초과 트리거를 폐기(on_scroll/on_mouse_move 명시). 차트/스크롤/마우스 이벤트 throttle + var당 state 작게 + 큰 blob을 단일 var에 넣지 말 것.

출처(primary): reflex.dev/docs/.../how-reflex-works · /events/event-actions · .venv/.../reflex/state.py(설치본 검증)

⑥ Caveats (방법론 한계)

Rolldown은 아직 beta — 2-3배는 벤더 릴리스 수치(magnitude는 중립 재현). delta 프로토콜은 설치된 버전 소스로 검증 → 해당 pinned 버전엔 정확하나 미래 릴리스서 drift 가능. Docker 7x/70%는 단일 Go 워크로드. 소스 품질은 전반적으로 강함(Reflex·SQLAlchemy·TimescaleDB·Docker primary + 설치 소스 + 중립 벤치). 백엔드 런타임/풀 공식/state 내부/cgroup 함정은 확증 실패 — confirmed 가이드로 제시 금지.
