Persona 1: Operator (운영자) {#persona-1-operator}

OP-01: 일일 야간 알람 검토 + 일괄 Acknowledge

시작 trigger: 오전 9시 주간 당직 교대. 야간 Critical 알람 확인이 첫 번째 업무.
사용자 목표: 지난 12시간 동안 발생한 Critical 알람을 모두 검토하고 acknowledge 처리.

[시작: 브라우저 열기 / http://localhost:14000]
          ↓ 로그인 없음 (No Auth — Gap 1)
[Step 1: Dashboard "/" — 실시간 센서 테이블]
  - DashboardRealtimeState.start_streaming 자동 실행
  - 전체 센서 상태 한눈에 파악
  - Critical 센서 수 확인 (우상단 stat cards)
          ↓ sidebar → "/alarms" 클릭
[Step 2: /alarms — Active Alarms 탭 (기본값)]
  - AlarmsState.initialize 실행
  - 현재 미확인 알람 수 확인
          ↓ "History" 탭 클릭
[Step 3: /alarms — History 탭]
  - AlarmsState.set_view_mode("history")
  - ISA-18.2 P1–P4 priority stat cards 노출
          ↓ 시간 범위 "12h" 또는 사용 가능한 최근 범위 선택
[Step 4: 12시간 필터 적용]
  - AlarmsState.set_hours_filter(12)
  - 알람 목록 재로딩
          ↓ Severity filter = "Critical" 선택
[Step 5: Critical 알람만 필터링]
  - AlarmsState.set_severity_filter("critical")
  - N개 Critical 알람 노출
          ↓ 각 알람 행 검토 후 "Select All" → "Acknowledge Selected"
[Step 6: 일괄 Acknowledge]
  - AlarmsState.select_all_visible()
  - AlarmsState.acknowledge_selected()
  - DB: alarm_history.acknowledged = true, acknowledged_at = NOW()
          ↓ 성공 toast 표시
[Step 7: 결과 확인]
  - 미확인 알람 카운트 0으로 갱신
  - History 탭 "총 알람" stat 재확인
          ↓ (선택) sidebar → "/alarms_hist" 클릭
[Step 8: /alarms_hist — 상세 이력 확인]
  - AlarmHistState.fetch_history() 실행
  - 날짜 범위: 어제 22:00 ~ 오늘 08:00
  - 처리 완료 확인

단계별 표:

Step Screen Action Expected Outcome Error Handler
1 / on_load 센서 테이블 30초 내 로딩 빈 테이블 + loading spinner
2 /alarms (Active) navigate 미확인 알람 목록 표시 error callout
3 /alarms (History) 탭 클릭 ISA P1-P4 카드 전환 동일 error callout
4 History set_hours_filter 알람 목록 12h분 재조회 빈 목록 + "데이터 없음"
5 History set_severity_filter Critical만 필터 필터 초기화 안내
6 History acknowledge_selected DB 커밋 + toast 개별 재시도 유도 메시지
7 History 자동 갱신 acknowledged count +N —
8 /alarms_hist fetch_history 날짜별 상세 이력 빈 상태 일러스트

사전조건: - alarm_history 테이블에 야간 Critical 알람 5개+ (acknowledged=false) - DashboardRealtimeState.start_streaming 정상 작동 - AlarmsState.acknowledge_selected 핸들러 구현 완료

사후조건: - DB: 해당 alarm_history 행들 acknowledged=true, acknowledged_at 기록 - UI: 미확인 알람 카운트 0, History 탭 "해결율" stat 증가

측정 가능한 성공 기준: Critical 알람 5개를 30초 이내에 일괄 acknowledge 완료.

Alternative Paths: - 알람이 없을 경우: Step 3에서 빈 목록 → 검토 완료 처리 - 일부 알람만 선택하고 싶은 경우: 개별 체크박스 사용 후 acknowledge_selected

Error Paths: - DB 연결 오류: error callout 표시, Refresh 버튼 노출 - 개별 acknowledge 실패: @event_with_error 데코레이터로 개별 토스트 에러

데이터 의존성: AlarmMonitor 10s 루프가 야간에 정상 실행되어 alarm_history에 레코드가 존재해야 의미 있음.

OP-02: 실시간 Critical 알람 발생 → 긴급 대응

시작 trigger: 근무 중 대시보드 상단 Critical 센서 배지가 갑자기 빨간색으로 점등.
사용자 목표: 발생 즉시 알람 내용을 파악하고 2분 이내 acknowledge + 조치 기록.

[Step 1: / (Dashboard) — 실시간 모니터링 중]
  - DashboardRealtimeState._fetch_data 30s 루프 실행 중
  - 센서 TMP-001 배지: NORMAL → CRITICAL 전환
  - Risk bar 빨간색으로 변경
          ↓ Critical 행의 "조치" 버튼 클릭
[Step 2: 센서 상세 정보 확인]
  - 현재값, 임계범위, 초과량, 판정시간 확인
  - (또는) sidebar → "/alarms_rt" 이동
          ↓ sidebar → "/alarms_rt" 클릭
[Step 3: /alarms_rt — 실시간 알람 페이지]
  - AlarmRTState.load_all_data 실행
  - 센서 카드 그리드에서 TMP-001 CRITICAL 카드 식별
  - 알람 카드: 현재값, 임계값, 시나리오 타입 확인
          ↓ 알람 카드의 "Acknowledge" 버튼 클릭
[Step 4: 단일 Acknowledge]
  - AlarmRTState.acknowledge_alarm("TMP-001")
  - DB: alarm_events UPDATE acknowledged=true
          ↓ 배지 상태 갱신 확인
[Step 5: 결과 확인 + 조치 기록]
  - 알람 카드 상태: CRITICAL (acknowledged) 표시
  - (선택) /alarms → History 탭 → 해당 알람 메모 확인
          ↓ 필요시 "/alarms" History에서 시나리오 분석
[Step 6: 시나리오 확인]
  - 알람 시나리오: RULE_BASE or AI_BASE 확인
  - 이상지속 여부 확인 (30분 이상 CRITICAL 지속?)

단계별 표:

Step Screen Action Expected Outcome Error Handler
1 / 자동 (30s cycle) Critical 배지 즉시 업데이트 스트리밍 중단 시 수동 새로고침
2 / 행 클릭 센서 상세 모달 or 행 확장 —
3 /alarms_rt on_load 카드 그리드 로딩 error toast
4 /alarms_rt acknowledge_alarm 카드 배지 acknowledged DB 오류 시 재시도 버튼
5 /alarms_rt 자동 갱신 미확인 카운트 감소 —
6 /alarms (History) navigate + filter 해당 알람 행 검색 —

사전조건: - 센서 TMP-001이 viewer_tag.show_alarm=true 설정 - AlarmMonitor가 실시간 임계값 초과 감지 + alarm_events INSERT - pg_notify → DatabaseEventListener → 프론트엔드 푸시 정상 동작

사후조건: - alarm_events: TMP-001 acknowledged=true, acknowledged_at 기록 - UI: Critical stat count 감소

측정 가능한 성공 기준: 알람 발생 후 2분 이내 acknowledge 완료.

BROKEN: /alarms_rt filter bar는 hardcoded 값으로 동작 불가 — Critical만 필터링 불가 (spec_01 Issue 2). 알람 페이지네이션 "Load More" 미작동 (spec_01 Issue 3).

OP-03: 특정 Sensor 현재값 확인

사용자 목표: 해당 센서의 현재값과 최근 추세를 빠르게 확인.

[Step 1: / (Dashboard)]
  - 센서 테이블에서 DP-003 행 찾기
  - 현재값, 상태 배지, 범위, 초과량 확인
          ↓ (현재값만으로 부족 시) sidebar → "/trend"
[Step 2: /trend — 트렌드 분석]
  - TrendState.load() 실행
  - Tag 선택: DP-003
  - 집계: 1m (최신 데이터)
  - 시간범위: 최근 1시간
          ↓ 차트 렌더링 확인
[Step 3: DP-003 트렌드 차트 확인]
  - Area 차트에서 최근 1시간 값 시각적 확인
  - 이상 급등/급락 패턴 식별
  - 하단 브러시로 특정 구간 확대
          ↓ 필요 시 현장 담당자에게 수치 공유 → CSV 내보내기
[Step 4: CSV 내보내기 (선택)]

단계별 표:

Step Screen Action Expected Outcome Error Handler

OP-04: 알람 임계값 일시 조정 (운영 변동기)

시작 trigger: 정기 청소 작업으로 DP-003 압력이 평소보다 높을 예정 (다음 2시간).
사용자 목표: 작업 시간 동안 DP-003 warning_high를 임시 상향 조정.

[Step 1: / (Dashboard)]
  - 센서 테이블에서 DP-003 행 찾기
  - 현재 범위 확인 (warning_high 값)
          ↓ DP-003 행의 "확인" 또는 "조치" 버튼 클릭
[Step 2: 센서 편집 다이얼로그 열기]
  - DashboardRealtimeState.open_edit_dialog() 실행
  - 현재 min/max/warning_low/warning_high/critical_low/critical_high 값 표시
          ↓ warning_high 필드 수정 (예: 5.5 → 7.0)
[Step 3: 임계값 수정]
  - DashboardRealtimeState.update_warning_high(7.0)
  - 입력값 검증 (critical_high보다 작아야 함)
          ↓ "저장" 클릭
[Step 4: DB 저장]
  - DashboardRealtimeState.save_sensor_info()
  - SensorService.update_sensor_metadata() 실행
  - DB: influx_qc_rule UPDATE warning_high=7.0
          ↓ 알람 모니터 다음 사이클(10s) 반영 확인
[Step 5: 반영 확인]
  - Dashboard에서 DP-003 범위 컬럼: 7.0으로 표시 확인
  - AlarmMonitor 10s 루프: 새 임계값으로 평가
          ↓ 2시간 후 원복 (동일 Flow 반복)
[Step 6: 원복]
  - 동일 편집 다이얼로그 → warning_high = 5.5 복원

OP-05: SCADA 알람 vs 시스템 알람 대조 확인

시작 trigger: 시스템 알람이 발생했으나 SCADA 콘솔에서는 알람이 없다고 보고받음.
사용자 목표: Rule-based vs AI-based 알람 비교를 통해 오탐 여부 판단.

[Step 1: sidebar → "/scada-alarm-comparison"]
  - ScadaAlarmComparisonState.load_comparison_data() 실행
  - 양측 알람 테이블 로딩
          ↓ 시간대 확인
[Step 2: 이중 테이블 대조]
  - 좌측: Rule-based 알람 (파란색 배지)
  - 우측: AI-based 알람 (보라색 배지)
  - Stat cards: 각 방법별 알람 카운트
          ↓ 동일 타임스탬프 알람 찾기
[Step 3: 특정 알람 교차 확인]
  - Rule-based 테이블에서 해당 시간대 알람 검색
  - AI-based 테이블에서 동일 시간대 확인
  - 두 테이블 모두에 있으면 → 실제 이상
  - 한쪽만 있으면 → 방법론 차이 확인 필요
          ↓ 상세 확인 필요 시 "/scada-alarms"로 이동
[Step 4: /scada-alarms — SCADA 실시간 로그]
  - ScadaAlarmState.load_alarm_logs() 실행
  - 실시간 스트리밍 시작: ScadaAlarmState.toggle_streaming()
  - Severity filter: 해당 수준으로 좁히기
          ↓ 결과 문서화 (화면 캡처 또는 노트)
[Step 5: 조치 결정]
  - AI 오탐 확인 시: 모델 재검토 필요 (→ AN-05 flow)
  - 실제 이상 확인 시: OP-02 긴급 대응 flow 적용

단계별 표:

Step Screen Action Expected Outcome Error Handler
1 /scada-alarm-comparison on_load 양쪽 테이블 렌더링 빈 상태 (scada_alarm_log 데이터 없음)
2 이중 테이블 시각 비교 방법별 카운트 stat cards —
3 이중 테이블 교차 검색 동일 타임스탬프 식별 수동 검색 (필터 없음)
4 /scada-alarms toggle_streaming 실시간 새 행 추가 LISTEN/NOTIFY 오류 시 수동 새로고침
5 — 판단 다음 flow 결정 —

사전조건: - scada_alarm_log 테이블에 데이터 존재 - alarm_history 테이블에 최근 알람 존재

사후조건: DB 변경 없음 (조회 전용)

측정 가능한 성공 기준: 5분 이내 오탐/실제 이상 판정 완료.

OP-06: 통신 상태 점검

시작 trigger: 특정 센서 데이터가 갑자기 업데이트되지 않는다는 이상 보고.
사용자 목표: 어떤 센서, 어느 시간대에 통신 장애가 있었는지 파악.

[Step 1: sidebar → "/comm"]
