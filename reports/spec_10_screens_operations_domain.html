1. 메타 개요

1.1 Operations 도메인 범위

Operations 도메인은 IoT 센서 실시간 운영, 태그 가시성 관리, 상위 클라우드 동기화, 통신 품질 모니터링 4개 영역을 커버한다. 이 스펙은 각 페이지의 UI 구조, 상태 바인딩, 이벤트 흐름, 성능 이슈, 알려진 결함을 SI 화면 설계서 기준으로 기술한다.

2.8 God-Class 분리 제안 (DashboardState legacy → 향후 DashboardRealtimeState)

현재 states/dashboard/state.py는 1,635 LoC로 spec_02에서 god-class 지적. 활성 대시보드는 DashboardRealtimeState를 사용하지만, 이도 성장 중. 제안 sub-component 분리:

가상 Sub-Component 현재 위치 책임 분리 근거
SensorCardComponent views/dashboard_realtime_view.py: sensor_tile() (L286-475) 개별 센서 카드 렌더링 (gauge + chart + badge) 독립 재사용 가능, 알람 페이지에서도 동일 카드 필요
MiniChartComponent views/dashboard_realtime_view.py: mini_chart() (L135-283) Recharts Area 차트 (status color, threshold lines) 트렌드 페이지와 중복 가능성. 별도 컴포넌트로 분리 시 재사용
AlarmTableComponent views/dashboard_realtime_view.py: alarm_monitoring_table() (L478-511) 실시간 알람 테이블 알람 도메인 페이지와 중복. alarms/ 도메인으로 이관 권장
SensorEditDialogComponent views/dashboard_realtime_view.py: sensor_edit_dialog() (L645-802) 센서 메타데이터 편집 폼 독립 컴포넌트화 시 viewer-tag 페이지에서도 재사용 가능
FullScreenChartDialogComponent views/dashboard_realtime_view.py: full_screen_chart_dialog() (L515-642) 전체화면 24시간 차트 트렌드 페이지 차트와 중복. 공통 컴포넌트 가능
KPITileRowComponent components/dashboard/kpi_tile.py: dashboard_kpi_tiles_compact() 4개 KPI 타일 이미 분리됨. 현행 유지

Streaming 동작 요약: start_streaming → initial _fetch_data() (timeout 10s) → 30초 sleep → _fetch_data() (timeout 28s) → 반복. 페이지 unload 시 stop_streaming 호출 없음. WebSocket 연결이 끊어지면 루프는 서버에서 계속 실행 가능.

KPI 토글 / chart blob 재직렬화 문제: formatted_sensors (@rx.var)는 캐싱되지 않으며 sensors와 chart_data 두 vars의 조합 연산. sensors 배열(N개)을 매 렌더마다 순회하며 chart_data 딕셔너리에서 조회. 센서 수 증가 시 O(N) 연산이 모든 UI 상태 변경마다 실행됨. 해결책: sensors 변경 시에만 재계산되도록 @rx.var(cache=True) 또는 별도 background event에서 처리.

2.9 save_sensor_info Dialog 동작

  1. settings 아이콘 클릭 → open_edit_dialog(tag_name, description, unit, min_val, max_val, warning_low, warning_high, critical_low, critical_high) 호출
  2. edit_* vars 일괄 설정, show_edit_dialog=True
  3. 사용자 폼 편집 → 각 필드 on_change 핸들러 (6개 별도 함수)
  4. "저장" 클릭 → save_sensor_info() background 실행
  5. SensorService.update_sensor_metadata() DB 업데이트
  6. 성공 시: show_edit_dialog=False, _fetch_data() 재로드
  7. 실패 시: last_update="Save error: {msg[:50]}" — toast/callout 없음, 사용자가 header timestamp 보지 않으면 알 수 없음

3.5 Toggle 반응성 분석

UI 즉시 반영 vs DB persist 흐름:

사용자 toggle 클릭
    → on_change → ViewerTagState.toggle_dashboard(tag_name)  [background=True]
    → async: DB UPDATE SET show_dashboard = NOT show_dashboard
    → await commit()
    → yield ViewerTagState.load_tags  [전체 재로드]
    → load_tags background 실행 → DB SELECT 전체 → self.tags 업데이트 → yield

문제점: toggle 클릭 → DB commit → 전체 테이블 재로드 사이에 UI 즉시 반영 없음. 즉, 토글 클릭 후 DB 왕복이 완료될 때까지 toggle UI는 클릭 전 상태 유지 → 사용자가 이미 처리됐는지 불확실.

권장 개선: optimistic update — toggle 직후 self.tags 내 해당 항목 상태를 즉시 반전, 이후 background에서 DB 커밋. 실패 시 원상 복구.

bulk action 흐름: show_all_dashboard → UPDATE viewer_tag SET show_dashboard = true → yield ViewerTagState.load_tags. 모든 태그에 일괄 적용. 진행 피드백 없음.

6.5 overall_success_rate 100% cap 버그 분석

# communication_state.py:66-81
@rx.var
def overall_success_rate(self) -> float:
    """전체 성공률 - FIXED: 100% cap added"""
    ...
    if expected_records > 0:
        rate = round(float(total_records / expected_records) * 100, 2)
        return min(rate, 100.0)  # Cap at 100%
    return 0.0

버그 내용 (spec_02에서 발견): 원래 min() 없이 계산했을 때 total_records > expected_records 상황 (DB 집계 오차 등)에서 100% 초과값 반환 가능. 현재 min(rate, 100.0) 패치 완료.

잔류 리스크: expected_records 계산도 동일 _df_hourly에서 별도 pandas 연산으로 수행 — 두 @rx.var의 pandas 연산이 독립적으로 실행되어 edge case에서 race condition 가능성 (단일 스레드 이벤트 루프이므로 실제 경쟁 조건은 아니나, 동일 데이터를 두 번 파싱하는 중복 문제).
