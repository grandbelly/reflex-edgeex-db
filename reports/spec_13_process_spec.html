spec_13 — 프로세스 명세서 (Process Specification)

작성 2026-05-29 · 작성자: bkend-expert + 메인 세션 (보강) · 정통 SI Process Spec — 비즈니스/데이터/시스템 흐름

본 문서는 흐름 단위 명세. 페이지/기능 단위가 아닌 프로세스 단위 — 트리거 → 단계 → 출력 → SLA → 실패 처리. 외부 시스템(센서 → DB → AI → 사용자) 간 데이터 이동 + 시간 예산을 추적.

데이터 프로세스

PROC-001 DATA
센서 데이터 수집 (data-injector → influx_hist)
트리거data-injector 컨테이너 무한 루프 (continuous)
주체ksys-local-data-injector / rpi-finished-data-injector
SLA새 row INSERT 지연 ≤ 1초 (실제 측정 안 됨)
의존ksys-dev-db UP + influx_tag 에 활성 tag 정의

흐름

[Sensor source]                  [data-injector]                [PostgreSQL/TimescaleDB]
        │                              │                                   │
        │ raw value (push or pull)     │                                   │
        ├─────────────────────────────→│                                   │
        │                              │ validate tag + value              │
        │                              │ build row (tag_name, ts, value)   │
        │                              │ INSERT influx_hist                │
        │                              ├──────────────────────────────────→│
        │                              │ AFTER INSERT trigger:             │
        │                              │   (1) refresh influx_latest view  │
        │                              │   (2) compute virtual_tag deps    │
        │                              ↓                                   ↓
        │                              done                            ← row in hypertable chunk

단계별

Step주체액션시간 예산실패 시
1sensorraw 측정값 emit≤ 100ms다음 cycle 재시도
2data-injectorvalidate + transform≤ 10ms잘못된 row drop, log
3asyncpgINSERT influx_hist≤ 50msretry × 3, fail → DLQ (현재 없음)
4TimescaleDBchunk routing + index≤ 20mschunk 생성 실패 → alarm
5triggervirtual_tag 계산 (pg_cron 1분 후)비동기다음 pg_cron run

알려진 이슈

  • data-injector 가 실제 어떤 sensor source 를 polling 하는지 코드 확인 필요 (가상 데이터 생성 vs 실제 SCADA)
  • backpressure 없음 — sensor burst 시 DB pool 고갈 가능
PROC-002 DATA
Continuous Aggregate Refresh (influx_hist → influx_agg_1m/10m/1h/1d)
트리거TimescaleDB background worker (자동, 1m/10m/1h/1d 주기)
주체PostgreSQL 17 + TimescaleDB 2.21.3
SLA새 데이터 → agg 반영 지연 ≤ 2분 (1m agg 기준)

흐름

[influx_hist (raw 1초~)]      [TS background worker]         [influx_agg_1m]
        │                              │                            │
        │ chunk 변경 감지               │                            │
        │←─ continuous_agg policy ─────┤                            │
        │                              │ refresh window 계산        │
        │                              │ (NOW - 2h, NOW)           │
        │                              │ aggregate 함수 실행:       │
        │                              │   AVG, MIN, MAX, COUNT     │
        │                              │ INSERT/UPDATE              │
        │                              ├───────────────────────────→│

알려진 이슈

  • HANDOFF.md 기록: continuous_agg 5개 중 일부가 dump 복원 시 누락 (2.21.3 → 2.27 catalog 차이)
  • refresh policy 확인 필요 (현재 1m agg는 1m schedule? 2m?)
PROC-003 DATA
Virtual Tag 계산 (pg_cron + VirtualTagScheduler)
트리거pg_cron 1분 주기 (PostgreSQL 내부) + VirtualTagScheduler 1분 (Python)
주체pg_cron + ksys-local-reflex-app 내 VirtualTagScheduler
SLA가상 태그 (PRESSURE_DIFF, RECOVERY_RATE, OPERATING_TIME, TOTAL_PRODUCT_VOLUME_1H) 1분 내 갱신

흐름

[pg_cron 1분 schedule]
        │
        ↓ SELECT calculate_virtual_tags()
[PL/pgSQL function]
        │ for each virtual_tag_def:
        │   SELECT dependency tags from influx_hist
        │   evaluate formula (예: PRESSURE_DIFF = inlet - outlet)
        │   INSERT virtual_tag_values
        │   INSERT influx_hist (synthetic row)
        ↓
[virtual_tag_values + influx_hist (가상 row)]

알려진 이슈

  • VirtualTagScheduler (Python) 와 pg_cron 이 둘 다 1분 — 중복 계산 가능성. 어느 것이 canonical?
  • 가상 태그 정의는 virtual_tag_definitions 테이블 — admin UI 없음 (PRD gap)

PROC-005 DATA
모델 학습 데이터 준비 (Training Wizard)
트리거TrainingWizardState 사용자가 Step 5 "학습 시작" 클릭

[Operator] [TrainingState]              [DB]                    [In-memory cache]
    │           │                         │                            │
    │ click "학습 시작"                    │                            │
    ├──────────→│                         │                            │
    │           │ validate inputs         │                            │
    │           │ SELECT feature_config   │                            │
    │           ├────────────────────────→│                            │
    │           │ SELECT influx_hist + agg│                            │
    │           ├────────────────────────→│                            │
    │           │ ← 대량 데이터            │                            │
    │           │ pandas DataFrame 구성    │                            │
    │           │ 6-step pipeline:        │                            │
    │           │   1. 전처리 (outlier)   │                            │
    │           │   2. interpolation      │                            │
    │           │   3. feature engineering│                            │
    │           │   4. model fit          │                            │
    │           │      (CPU bound, blocking — 우려)                    │
    │           │   5. walk-forward valid │                            │
    │           │   6. metric 계산        │                            │
    │           │ _training_cache[tag] = (result, model)               │
    │           ├──────────────────────────────────────────────────────→│
    │ ← yield progress (12 회)            │                            │
    │←──────────┤                         │                            │
    │ Step 6 UI                           │                            │
    │           │                         │                            │
    │ click "모델 저장"                    │                            │
    ├──────────→│ save_model (Day 3 refactored)                        │
    │           │ asyncio.to_thread(pickle.dumps, model)               │
    │           │ INSERT model_registry (BYTEA)                        │
    │           │ bulk INSERT training_evaluation (36 rows in 1 round-trip)
    │           ├────────────────────────→│                            │
    │           │                         │ ✓                          │

알려진 이슈

  • 학습은 background event 안에서 실행되지만 model.fit() 자체는 CPU bound — event loop 차단 가능성
  • _training_cache 는 모듈 레벨 dict — container restart 시 휘발
  • 학습 취소 불가 (Cancel 버튼 없음, 결함 W-01)

PROC-024 SYS

흐름 (저장 — Day 3 refactored)

[save_model event handler]
   ↓ trained_model = _get_cached_model(tag)
   ↓ model_pickle_bytes = await asyncio.to_thread(pickle.dumps, trained_model) ← Day 3 fix
       (event loop 차단 회피)
   ↓ INSERT model_registry (model_pickle = BYTEA)

흐름 (로드)

[ForecastScheduler cycle]
   ↓ SELECT model_pickle FROM model_registry WHERE is_deployed=true
   ↓ asyncio.to_thread(pickle.loads, BYTEA)  ← 동일하게 offload
   ↓ model.predict(...)

알려진 이슈

  • pickle.loads 자체가 보안 risk (audit H-03 — DB 침해 시 컨테이너-root RCE)
  • 완화: DB 쓰기 권한 분리, 향후 ONNX/TFLite 마이그레이션 검토 (ADR 후보)
