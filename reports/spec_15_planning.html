1. Executive Summary

제품 한 줄 설명: KSYS는 Raspberry Pi 위에서 실행되는 소규모 수처리·해수담수화 플랜트 전용 IoT 실시간 관제 + AI 예측 플랫폼이다. 30초 센서 갱신, ISA-18.2 알람 관리, 10분 ML 예측, 트렌드 분석을 단일 웹 대시보드에 통합한다.

4-Perspective 가치 테이블

관점내용
Problem (문제) 소규모 정수 처리 사이트(풍도)의 운영자는 실시간 센서 이상, 알람 인지, 과거 트렌드 분석, 미래 예측을 별도 도구로 수행하거나 수작업으로 처리하고 있다. 통합 관제 부재로 P4 Emergency 알람 누락 위험, 알람 피로, 조용한 모델 성능 저하 문제가 동시에 발생한다.
Solution (해결책) KSYS는 Reflex(Python Full-Stack) 기반 단일 웹 앱으로 실시간 센서 상태(30s), ISA-18.2 알람 라이프사이클(10s), 10분 간격 ML 예측(Prophet / Auto-ARIMA / XGBoost), 센서 트렌드 분석(1m~1d 집계), 6단계 학습 마법사를 하나의 사이드바 네비게이션 안에 통합한다. 하드웨어는 RPI 5 단일 노드 + TimescaleDB로 현장 엣지 배포가 가능하다.
Functional UX Effect (기능적 UX 효과) 운영자는 대시보드 한 화면에서 NORMAL/WARNING/CRITICAL 배지, 리스크 바, 알람 카운트를 즉시 확인한다. 알람 발생 → 확인 → 일괄 acknowledge 흐름이 클릭 3번 이내로 처리된다. 공정 엔지니어는 /trend에서 30일 데이터를 6줄 CSV 내보내기로 추출하고, /forecast에서 신뢰구간 포함 10분 갱신 예측 차트를 추가 도구 없이 열람한다.
Core Value (핵심 가치) 알람-대응 지연 단축, AI 기반 임계값 위반 선제 경고, 알람 발생~확인 완전 감사 추적(audit trail). 단일 RPI 5 하드웨어(~$80) + OSS 스택으로 대형 산업 SCADA 대비 1/10 이하 비용에 AI 예측 기능을 번들로 제공한다.

2. 비전 (Vision)

우리가 만드는 것

단일 사이트 정수처리·해수담수화 IoT 통합 관제 플랫폼
한 대의 Raspberry Pi 5 위에서, 현장 LAN 혹은 Cloudflare tunnel을 통해 접근 가능한 웹 대시보드로서 — 센서 실시간 모니터링, 알람 관리, AI 예측, 트렌드 분석을 단일 앱에 통합한다. 인터넷이 없어도 동작하는 엣지 우선(Edge-First) 아키텍처이며, 소규모 운영팀(3-10인)을 대상으로 한다.

포함 (In Scope)

  • 단일 사이트 단일 RPI 5 노드 운영
  • 실시간 센서 모니터링 (30초 갱신)
  • ISA-18.2 4-등급 알람 라이프사이클
  • Prophet / Auto-ARIMA / XGBoost 10분 예측
  • TimescaleDB 기반 시계열 집계 + 트렌드 분석
  • 6단계 가이드 ML 학습 마법사
  • Cloudflare tunnel 선택적 원격 접근
  • 단일 사이트 복수 RPI 노드 확장 (Q2)

제외 (Out of Scope)

  • 멀티 플랜트 SaaS (다중 고객 테넌시)
  • 모바일 앱 (iOS / Android 네이티브)
  • 공급망 / ERP / 자산관리 시스템
  • OPC-UA / Modbus 직접 프로토콜 연결
  • 국가 인프라급 SCADA 대체
  • 실시간 비디오 감시
  • 클라우드 전용(SaaS) 호스팅 모델

시장 규모 (추정)

TAM (총 시장): 국내 소규모 수처리 시설 (읍면 단위, 섬 지역, 지자체 직영) 수천 개소. 각 사이트당 IoT 관제 도입 비용 추정 500만-3,000만원 → 약 5,000억-3조원 규모 (공공 인프라 예산 포함).

SAM (실제 접근 가능): RPI 수준 엣지 장비로 충분한 소규모 사이트 (센서 30개 이하, 운영 인원 10인 미만). 추정 300-500개소 × 300만원 = 약 90억-150억원.

SOM (현실적 목표 3년): 10개소 × 300-500만원 유지보수 계약 = 연 3,000-5,000만원 수익 목표.

주의: 위 수치는 현재 정보 없이 상향 추정. Q4 사업화 검토 시 실제 시장 조사 필요.

9. 의사결정 기록 (ADR — Architecture Decision Record)

ADR-01: Reflex 채택 vs Django/Flask + Vue/React

결정Reflex (Python Full-Stack) 채택
컨텍스트단독 개발자가 IoT 대시보드를 빠르게 구축해야 하는 상황. ML 코드(Python)와 UI 코드를 분리하지 않고 단일 언어로 유지하는 것이 생산성에 유리.
이유 1) Python 단일 언어로 프론트·백엔드·ML 파이프라인 통합 가능.
2) WebSocket 기반 실시간 상태 동기화가 Reflex에서 rx.event + rx.State로 구조화됨.
3) RPI 같은 제한된 환경에서 Node.js 빌드 없이 Python만으로 배포 가능.
트레이드오프Reflex는 Django/Flask 대비 생태계 성숙도 낮음. 0.8.x 버전으로 breaking change 빈번. 컴포넌트 커스터마이징 제약.
결과현재 prod 운영 중 (Reflex 0.8.16). 15개 라우트 HTTP 200 확인 (verify_2026-05-20.html).
재검토 조건Reflex 1.x 이상 안정화 전까지 유지. 멀티 사이트 SaaS 전환 시 별도 검토.

ADR-02: TimescaleDB 채택 vs InfluxDB

결정TimescaleDB (PostgreSQL 확장) 채택
컨텍스트IoT 시계열 데이터 저장소 선택. 알람 이력·모델 레지스트리·예측 결과 등 비시계열 관계형 데이터도 동일 DB에 통합 관리 필요.
이유 1) PostgreSQL 기반 → 기존 SQL 도구, pg_notify, psycopg2 생태계 그대로 활용.
2) 시계열(influx_hist) + 관계형(model_registry, alarm_history, viewer_tag) 단일 DB 통합 가능.
3) InfluxDB는 Flux 쿼리 언어 별도 학습 필요 + 관계형 데이터 저장 불편.
4) pg_cron으로 스케줄 작업(continuous aggregate 갱신)을 DB 레이어에서 처리 가능.
트레이드오프InfluxDB 대비 순수 시계열 쓰기 성능이 낮을 수 있음. TimescaleDB 버전 관리(2.21.3↔2.27 catalog 차이) 복잡성.
결과influx_hist 294K rows, 6 hypertables + 5 continuous aggregates (2.21.3→2.27 catalog 이슈 일부). 정상 운영 중.
재검토 조건센서 수 50개 초과, 1초 이하 샘플링 필요 시 InfluxDB 또는 QuestDB 재검토.

ADR-03: Cloudflare Tunnel 채택 vs nginx + Let's Encrypt

결정Cloudflare Tunnel 채택 (cloudflared)
컨텍스트풍도 현장 RPI를 외부에서 접근 가능하게 할 방법 필요. 현장 고정 공인 IP 없음, ISP 방화벽 포트 개방 불가.
이유 1) 공인 IP 없어도 outbound 연결만으로 ksys.kr 도메인 접근 가능.
2) nginx + Let's Encrypt는 공인 IP 또는 DNS 챌린지 가능한 도메인 필요.
3) TLS 자동 관리 (Cloudflare 레이어에서 처리).
4) 초기 설정 단순 (cloudflared 단일 바이너리 + 토큰).
트레이드오프 Cloudflare 의존성 도입. 토큰 노출 시 치명적 (C1 취약점 발생 원인). 인증 없는 현재 상태에서는 터널이 공격 표면 확대 요소.
결과현재 C1 취약점(토큰 평문 커밋) 발생. Q1 Day 1 토큰 교체 + .env 이관 예정.
재검토 조건Q2 인증 도입 후 Cloudflare Access 정책 추가하여 보안 강화. 장기적으로 내부망 전용 시 tunnel 제거 검토.

ADR-04: Raspberry Pi 5 채택 vs x86 Mini PC

결정Raspberry Pi 5 채택
컨텍스트현장 임베디드 컨트롤러 하드웨어 선택. IoT 데이터 수집 + 웹 서버 + DB + ML 스케줄러를 단일 노드에서 실행해야 함.
이유 1) 단가 ~$80 (RPI 5 4GB) vs x86 Mini PC ~$150-300.
2) 전력 소비 ~25W vs x86 mini PC ~65W — 현장 전원 제약 환경에서 유리.
3) GPIO 확장 가능성 (향후 직접 센서 연결).
4) 폼 팩터 작음 — 제어반 내부 설치 용이.
트레이드오프 ARM64 아키텍처 — 일부 ML 라이브러리 (XGBoost wheel 등) 빌드 시간 증가. CPU 성능 제약 — 복잡한 ML 학습 시 수십 분 소요. eMMC 없음 (SD/NVMe) — 스토리지 내구성 관리 필요.
결과현재 정상 운영 중. Docker 이미지 4.49GB → Q2에서 경량화 필요.
재검토 조건ML 학습 빈도 증가로 학습 시간이 업무 방해 수준 이상 시 x86 mini PC 또는 클라우드 학습 서버 분리 검토.

ADR-05: Pickle 직렬화 채택 vs ONNX / TFLite / skops

결정Python Pickle 채택 (현재) — 위험 등록 완료
컨텍스트ML 모델(Prophet, Auto-ARIMA, XGBoost)을 DB(model_registry.model_pickle BYTEA)에 저장 후 스케줄러에서 로드.
이유 (채택 당시) 1) Prophet / StatsForecast 객체는 ONNX 변환 미지원 — pickle이 사실상 유일한 직렬화 방법.
2) 구현 속도: pickle.dumps/loads 2줄로 완성.
3) XGBoost는 ONNX 지원하나 Prophet과 통일성 위해 동일 경로 사용.
트레이드오프 보안 위험: DB 침해 시 malicious pickle INSERT → 스케줄러 실행 시 RCE. Security Audit H3: "컨테이너 루트 RCE — 모든 RPI에 다음 스케줄 사이클에 실행".
결과현재 prod 운영 중이나 R-04 위험 등록. Q3 HMAC 서명 검증 + XGBoost ONNX 전환 계획.
재검토 조건Q3 보안 스프린트 시 Prophet=HMAC+pickle, XGBoost=ONNX, Auto-ARIMA=skops 혼합 전략 검토.

ADR-06: 단일 Reflex 앱 아키텍처 vs 마이크로서비스 분리

결정단일 Reflex 앱 (Monolith) 채택
컨텍스트IoT 관제 + 알람 + ML 학습 + 예측 스케줄러를 하나의 애플리케이션으로 구성할지, 마이크로서비스로 분리할지.
이유 1) 단독 개발자 — 서비스 간 통신, 배포 파이프라인 복잡성 감당 불가.
2) RPI 단일 노드에서 컨테이너 오케스트레이션(k8s) 비현실적.
3) 현재 Reflex 앱 + 별도 scheduler 컨테이너 2개 분리는 이미 적절한 관심사 분리.
트레이드오프State 파일 비대화 위험 (현재 20개 state, god class 존재). 특정 기능 독립 확장 불가.
결과ksys_app/ monolith + schedulers/ 별도 컨테이너. Q2 Refactor Sprint에서 내부 모듈 분리.
재검토 조건사이트 수 5개 초과, 개발팀 3인 이상 시 마이크로서비스 전환 검토.

ADR-07: Python asyncio 기반 스케줄러 vs Celery / APScheduler

결정Python asyncio + pg_cron 혼합 채택
컨텍스트10초 알람 모니터링, 10분 예측, 1시간 성능 집계, 가상 태그 계산 등 다양한 주기의 백그라운드 작업 필요.
이유 1) asyncio Task는 Reflex State와 동일 이벤트 루프 — DB 연결 공유 용이.
2) pg_cron은 TimescaleDB에 이미 포함 — 별도 스케줄러 프로세스 없이 DB 레이어 스케줄 가능.
3) Celery는 Redis/RabbitMQ 브로커 추가 의존성 — RPI 자원 낭비.
트레이드오프asyncio Task cancel 비표준화 → zombie task 위험 (R-08). pg_cron은 dev 환경에서 비활성 (PG17/18 ABI 호환 이슈).
결과ForecastScheduler timeout 이슈 발생 → agentic-pipeline으로 해결 (HANDOFF.md Round 3). dev pg_cron 비활성 중.
재검토 조건Q2 asyncio 표준화 완료 후 유지. 작업 수 50개 초과 시 APScheduler 도입 검토.

12. 결론 + Call to Action

현황 평가

KSYS는 현재 기능은 완성되었지만 운영 품질이 미완성인 상태다. 15개 라우트 HTTP 200, 3 페르소나 18개 User Flow 지원, ML 예측·알람 관리·트렌드 분석 핵심 기능 모두 작동 중이다. 그러나 보안 Critical 3건(C1·C2·C3), High 5건, 코드 품질 결함 10건, 인증 없음이 현재 운영 환경에 동시에 존재한다. 풍도 사이트가 Cloudflare Tunnel로 공개 노출된 상태에서 이 취약점들은 즉각적 위험이다.
