1. 서론 (Introduction)

1.1 목적 (Purpose)

본 문서는 edgeEX IoT 정수처리 통합 관제 시스템의 기능적/비기능적 요구사항을 IEEE 830-1998 및 ISO/IEC/IEEE 29148:2018 형식으로 명세하는 것을 목적으로 한다. 본 SRS는:

  • 개발팀의 구현 baseline 으로 사용된다.
  • QA 팀의 검증 baseline 으로 사용된다 (각 요구사항은 spec_05_test_plan의 TC-ID 와 추적된다).
  • 발주자 / 운영자 / 유지보수 인력이 시스템에 대해 동일한 이해를 공유하기 위한 합의문 역할을 한다.
  • 향후 변경 요구의 영향 범위 판단을 위한 기준 문서로 사용된다.

1.2 범위 (Scope)

본 SRS 가 적용되는 시스템은 Raspberry Pi 5 단일 노드에서 동작하는 Reflex 0.8 기반 정수처리 IoT 통합 관제 웹 애플리케이션이다. 시스템 구성:

  • Reflex (Python full-stack) 애플리케이션 — Docker 컨테이너 rpi-finished-reflex-app
  • TimescaleDB 2.21.3 + PostgreSQL 17 — Docker 컨테이너 rpi-finished-pgai-db
  • Cloudflare Zero Trust tunnel — 외부 접근 채널
  • 14 활성 페이지 + 24 State 클래스 + 201 event handlers + 17 DB 테이블 + 6 schedulers

범위 외 (Out of Scope):

  • 다중 사이트 / 다중 플랜트 운영 (가정: 단일 정수처리 시설)
  • 모바일 전용 UI (데스크탑 1080p 우선)
  • 현재 비활성 상태인 /ai (RAG chat) — 미래 활성화 시 별도 SRS 추가본 필요
  • OT 네트워크 직접 연결 (시스템은 IT 측 후처리 데이터만 처리)

1.5 개요 (Overview)

본 문서는 8개 주요 섹션으로 구성된다. §2 는 시스템의 전체 그림 (제품 관점, 페르소나, 제약, 가정)을 제시하며, §3 은 9 개 도메인에 걸친 93 개 기능 요구사항을, §4 는 7 개 카테고리의 55 개 비기능 요구사항을 명세한다. §5 는 외부 인터페이스 8 개, §6 은 요구사항 ↔ 기능 ↔ 테스트 추적 매트릭스, §7 은 SHALL/SHOULD/MAY 우선순위 정책, §8 은 변경 통제 절차를 다룬다.

8. 변경 통제 (Change Control)

8.1 요구사항 변경 절차

  1. Change Request 작성 — 변경 사유, 영향 도메인, 우선순위 (SHALL/SHOULD/MAY) 명시.
  2. 영향 분석 — RTM 역방향 추적으로 영향받는 화면 spec / 기능 spec / test case 식별.
  3. spec 갱신 순서: (a) spec_15 기획 → (b) spec_04 PRD → (c) 본 SRS (spec_16) → (d) spec_12 기능 spec → (e) spec_06~11 화면 spec → (f) spec_05 test plan.
  4. 코드 변경 — 갱신된 spec 을 baseline 으로 구현.
  5. 검증 — 영향 받은 TC 재실행 + 신규 TC 작성.
  6. 승인 — 영향 도메인별 owner sign-off.

8.2 SHALL 변경 시 강제 규칙

  • SHALL 요구사항의 제거/약화는 stakeholder 승인 필요.

  • 안전 critical (REQ-F-ALM-*, REQ-NF-REL-002 알람 누락 0건)은 변경 불가.
