핵심 함의: TrainingState의 모든 메서드는 TrainingWizardState가 상속함. 메서드 본문을 queries.py 같은 외부 모듈에 pure function으로 옮기면 — 자식 클래스(TrainingWizardState)는 그 메서드를 잃음. 따라서 추출 패턴은: 
# queries.py
async def list_configs_for_tag(tag_name: str) -> list[str]:
    async with get_async_session() as session:
        return [c['config_name'] for c in await FeatureConfigService(session).list_configs(tag_name=tag_name)]

# state.py — 메서드 자체는 클래스에 남아야 상속됨
@rx.event(background=True)
async def filter_configs_for_tag(self):
    try:
        configs = await list_configs_for_tag(self.selected_tag)
        async with self:
            self.available_feature_configs = configs
            yield
    except Exception as e:
        console.error(f"Filter configs failed: {e}")
즉 wrapper 메서드는 state.py에 남고, body의 pure 부분만 이동. 메서드당 절약은 deep-1 리포트가 추정한 것보다 작음.

4. 그러면 어떻게 할 것인가

세 가지 현실적 옵션:

옵션state.py 목표 LoC방법risk가치
O1. 목표 하향 + B 그대로 ~830L B-A-B-A 그대로 진행. AC-1을 ≤850L로 수정. 다른 AC(2/3/4)는 그대로. 낮음 중 — 변화는 있지만 dramatic하지 않음
O2. 적극 추출 (C 경로 변형) ~600L 가능 start_training을 작은 메서드 여러 개로 쪼개기 (예: _step_load_data, _step_preprocess, _step_fit, _step_evaluate) — 각각 state 메서드로 남기지만 길이 단축. progress_callback 패턴 + 메서드 분리 둘 다 적용. 높음 상 — 진짜 600L 달성. 단 regression 위험 큼.
O3. 추출 보류, scope 재정의 (미적용) Stage 4-1은 LOW+MED만 추출 (queries.py + validators.py). start_training/save_model은 Stage 4-2 별도 작업으로 분리. AC-1 목표는 ~900L (소폭 개선) 로 낮춤. 매우 낮음 중하 — 진척은 작지만 안전하게 baseline 구축

추가로 검토할 점

  • TrainingWizardState 영향: 어느 옵션을 가도 wrapper 메서드는 state.py에 남아야 함. 자식 클래스가 override할 수 있는 표면이 줄어들지 않게 주의.
  • save_model의 SQLAlchemy session: 10개의 self.* mutation + 13개의 ORM marker. session 객체를 외부 함수에 넘기면 transaction boundary가 흐려짐. 차라리 query helper만 외부로, ORM write는 state.py 잔류 권장.
  • start_training의 yield 22회: 단순 progress_callback으로는 yield 시점 보존 어려움. 각 단계가 generator처럼 진행상황을 emit. callback 대신 sub-method 분해(O2)가 더 자연스러울 수 있음.

  2. start_training/save_model을 이번 Stage에서 건드릴 것인가, 다음 Stage로 미룰 것인가? O3 vs O1/O2 선택.
